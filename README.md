# Bank Expense Limits

![CI](https://github.com/Ratila1/bank-expense-limits/actions/workflows/ci.yml/badge.svg)

Микросервис для банка: принимает расходные операции в любой валюте, переводит их в USD по курсу
биржи и помечает операции, превысившие месячный лимит по категории расходов (`product` / `service`).

## Возможности

- Приём расходных операций (`POST /api/v1/transactions`) с пересчётом в USD по дневному курсу закрытия.
- Месячные лимиты в USD отдельно для товаров и услуг; по умолчанию 1000 USD.
- Флаг `limit_exceeded` с учётом лимита, действовавшего на момент операции.
- Клиентский API: установка лимита, список лимитов, список операций, превысивших лимит.
- Курсы валют кэшируются в собственной БД, внешний API вызывается только при отсутствии курса.
- Устойчивость к сбоям внешнего API и корректная работа при параллельных запросах одного клиента.

## Технологии

Java 21, Spring Boot 4, Spring Web MVC (виртуальные потоки), Spring Data JPA, PostgreSQL, Flyway,
MapStruct, Lombok, springdoc-openapi, Logbook, Micrometer и Actuator, Docker и Docker Compose,
GitHub Actions. Тесты: JUnit 5, AssertJ, Mockito, Testcontainers, WireMock.

## Быстрый старт

Нужны Docker и (для локального запуска) JDK 21.

### Через Docker Compose

```bash
cp .env.example .env        # при желании впишите свой TWELVEDATA_API_KEY
docker compose up --build
```

Сервис: http://localhost:8080, Swagger UI: http://localhost:8080/swagger-ui.html,
health-check: http://localhost:8080/actuator/health.
Остановка: `docker compose down` (с удалением данных: `docker compose down -v`).

### Локально (разработка)

```bash
export TWELVEDATA_API_KEY=ваш_ключ     # PowerShell: $env:TWELVEDATA_API_KEY = "ваш_ключ"
./mvnw spring-boot:run
```

PostgreSQL поднимается автоматически из `compose.dev.yaml` (Spring Boot Docker Compose Support), профиль `dev`.
Без ключа сервис тоже работает: операции в валюте без известного курса сохраняются со статусом
`PENDING_RATE` и досчитываются позже (см. «Устойчивость к сбоям»).

Ключ можно получить бесплатно на [twelvedata.com](https://twelvedata.com).

## API

Документация: Swagger UI (`/swagger-ui.html`), спецификация: `/v3/api-docs`.
Все ошибки возвращаются в формате `ProblemDetail` (RFC 9457).

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/transactions` | приём расходной операции (интеграция с банковскими сервисами) |
| `POST /api/v1/client/limits` | установить новый лимит |
| `GET /api/v1/client/limits?account=` | все лимиты счёта |
| `GET /api/v1/client/transactions/exceeded?account=` | операции, превысившие лимит, с данными лимита |

Пример операции:

```json
{
  "account_from": "0000000123",
  "account_to": "9999999999",
  "currency_shortname": "KZT",
  "sum": 10000.45,
  "expense_category": "product",
  "datetime": "2022-01-30T00:00:00+06:00"
}
```

Пример установки лимита (дата устанавливается сервисом):

```json
{ "account": "0000000123", "expense_category": "product", "limit_sum": 1000.00 }
```

В ответе по превышениям к полям операции добавляются `limit_sum`, `limit_datetime` и
`limit_currency_shortname` (всегда `USD`).

## Логика лимитов

1. Курс берётся на дату операции, сумма переводится в USD (`sum / курс`, округление `HALF_UP` до 2 знаков).
2. Находится лимит, действовавший на момент операции: последний по дате установки, не позже времени
   операции (SQL: JOIN с подзапросом `MAX(set_at)`). Если лимитов нет, создаётся лимит по умолчанию
   1000 USD с датой `1970-01-01`; он виден в `GET /limits`.
3. Считается сумма расходов того же счёта и той же категории за календарный месяц операции.
4. `limit_exceeded = true`, если сумма за месяц вместе с текущей операцией **строго больше** лимита.
   Остаток ровно 0 превышением не считается.
5. Новый лимит действует только на операции, совершённые после его установки; флаги прежних операций
   не меняются. Лимиты не редактируются, можно только добавить новый (дата ставится сервисом из `Clock`).

Пример (случай 1 из задания): лимит 1000 USD с 1 января, операции 500 и 600 USD: у второй
`limit_exceeded = true`. Лимит 2000 USD с 10 января, операция 100 USD 11 января: `false`.

## Часовой пояс

Границы календарного месяца определяются в часовом поясе `app.zone` (**по умолчанию UTC**, настраивается).
В нём же вычисляется дата для запроса курса. В БД время хранится как `TIMESTAMPTZ` (момент времени),
в ответах API даты отдаются со смещением `app.zone`. Операции с разными смещениями во входных данных
приводятся к одному моменту времени, поэтому попадают в «свой» месяц однозначно.

## Получение курсов и устойчивость к сбоям

Источник: [Twelve Data](https://twelvedata.com), пары `USD/<валюта>`, интервал `1day`, курс закрытия (`close`).
Курс хранится как «единиц валюты за 1 USD».

Порядок поиска курса на дату операции:

1. **Своя БД**: точный курс на эту дату. Внешний (платный) запрос не выполняется.
2. **Внешний API**: берётся свеча на дату операции (`CLOSE`); в выходной и праздник последнее закрытие
   до этой даты (`PREVIOUS_CLOSE`). Результат сохраняется в БД.
3. **Запасной курс**: если API недоступен, используется последний известный курс из БД на эту дату или раньше.
4. **`PENDING_RATE`**: если курса нет совсем, операция всё равно сохраняется (данные не теряются) со статусом
   `PENDING_RATE`; планировщик раз в минуту (по 50 штук) пробует получить курс и досчитывает операцию.

Параметры клиента (`rates.provider.*`): таймаут соединения 2 с, чтения 3 с, до 3 попыток с растущей
паузой (300 мс, 600 мс). Повторяются только временные сбои (таймаут, сеть, HTTP 429 и 5xx); ошибки 4xx,
неверный ключ и неподдерживаемая пара не повторяются. Запрос курса выполняется до открытия транзакции БД,
поэтому медленный внешний API не держит блокировку счёта. Ключ API маскируется в логах.

## Параллельные запросы

Транзакции одного клиента могут приходить одновременно. Перед чтением месячной суммы сервис берёт
`pg_advisory_xact_lock` по ключу «счёт:категория» внутри DB-транзакции; блокировка снимается при коммите.
Параллельные запросы по одной паре выстраиваются в очередь и каждый видит уже сохранённые предыдущие,
а разные счета и категории не блокируют друг друга. Уровень изоляции `READ COMMITTED` (по умолчанию в PostgreSQL),
иначе запрос после ожидания не увидел бы чужие коммиты.

## Допущения и ограничения

- Лимит привязан к паре (счёт `account_from`, категория расходов): в задании говорится о клиенте, а клиента
  в данных представляет счёт.
- `GET` по лимитам и превышениям требует параметр `account`.
- Флаг считается в порядке поступления операций, а не в порядке их `datetime`: операция, пришедшая позже
  с более ранней датой, учитывается в месячной сумме, но флаги уже сохранённых операций не пересчитываются.
- Операция, досчитанная из `PENDING_RATE`, считается по сумме месяца на момент досчёта.
- Курс «за сегодня» сохраняется как есть и больше не обновляется.
- Для даты в будущем и для даты без биржевых данных используется последнее закрытие.
- Авторизации нет (по условию задания); Actuator и Swagger нельзя выставлять в публичную сеть без защиты.
- Возможность параллельно получать курсы для разных валют на виртуальных потоках (необязательный пункт) не реализована.

Автотесты запускаются одной командой; из окружения нужен только Docker (Testcontainers сам поднимает PostgreSQL):

```bash

```

| Уровень | Классы | Тестов | Что проверяют |

| Интеграционные | `LimitExceededFlagTest`, `TransactionRateFlowTest` | 26 | логика флага `limit_exceeded` на реальной БД; курсы, сбои провайдера, `PENDING_RATE` и досчёт планировщиком |
| Параллельность | `ConcurrentTransactionsTest` | 2 | 20 одновременных транзакций на виртуальных потоках |
| Сквозной | `ExpenseLimitsE2ETest` | 9 | «случай 1» из задания через HTTP, формат ошибок, недоступные операции |
| Контекст | `BankexpenselimitsApplicationTests` | 1 | приложение стартует, миграции применяются, схема сходится с сущностями |

Основные сценарии логики флага:

- оба примера из таблицы задания («случай 1» и «случай 2») шаг за шагом, включая то, что новый лимит
  не меняет флаги прежних операций;
- граничные случаи: остаток лимита ровно 0 (`false`), превышение на одну копейку (`true`), лимит по умолчанию
  1000 USD, смена лимита внутри месяца, переход на новый месяц, граница месяца определяется в UTC, а не по
  смещению операции;
- операция с датой до установки нового лимита проверяется по лимиту, действовавшему на её дату;
- независимость категорий и счетов; расчёт идёт по сумме в USD, а не в исходной валюте.

Параллельность: 20 одновременных операций по 100 USD при лимите 1000 USD дают ровно 10 с `limit_exceeded = false`
и ровно 10 с `true`; для двух категорий на одном счёте итоги независимы. Тест проверяет блокировку
`pg_advisory_xact_lock`: без неё потоки видели бы один и тот же остаток.

Сквозной тест `ExpenseLimitsE2ETest` поднимает приложение на реальном порту (`RANDOM_PORT`), PostgreSQL в Testcontainers
и WireMock вместо Twelve Data (курс 480 KZT за USD), а HTTP-вызовы делает через `RestClient`. Он устанавливает лимиты,
отправляет операции «случая 1» в тенге, запрашивает список превышений и проверяет, что вернулись ровно две операции
(3 и 13 января) с лимитами 1000 и 2000 USD, датами их установки и валютой `USD`. Дополнительно проверяются ответы
`ProblemDetail` с кодом 400 на неверный счёт, категорию, валюту и отрицательную сумму, а также код 405 на попытку
изменить лимит.

### Как устроены тесты

- **Время.** Бин `Clock` в тестах заменён управляемыми часами (`MutableClock`), поэтому сценарии «переводят время»:
  1 января ставится один лимит, 10 января другой.
- **Внешний API.** Всегда WireMock; настоящий Twelve Data в тестах не вызывается, ключ не нужен.
- **База данных.** PostgreSQL в Testcontainers (`@ServiceConnection`); контейнер и контекст Spring переиспользуются между
  классами, таблицы очищаются перед каждым тестом, поэтому тесты не зависят друг от друга и порядка запуска.
- **Профиль `test`**: короткие таймауты и отложенный планировщик (`application-test.properties`).
- Классы называются `*Test`: именно их запускает surefire в `./mvnw verify`, на этих же тестах работает CI.


```bash
./mvnw -B verify      # нужен запущенный Docker (Testcontainers)
```
